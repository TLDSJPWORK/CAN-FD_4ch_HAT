# 4ch CAN FD HATを3枚使った12ch実験で変更したこと

Raspberry Pi 5に4ch CAN FD HATを3枚接続し、SPI・CANドライバーと試験設定を調整した。対策後は、Classic CANの960 fps/chとCAN FDの434 fps/chで、それぞれ全12ch同時に3時間を完走した。両試験とも全24方向の欠落・予定外受信・重複は0だった。以下の数値は未製品化の試作構成での実験結果。

## 比較の基準

- **4ch HATの配布例**はリポジトリの `b9013c4164419481d4b76cf8d67ec368179a9805`。SPI0/1に各2台、20 MHzのMCP2518FDを配置する。FD設定例は500 kbps／2 Mbps、サンプルポイント0.75／0.8、送信キュー長1000。[起動設定例](../../examples/config.txt)・[CAN設定例](../../examples/up.sh)
- **ドライバーの標準版**は試験機のRaspberry Pi Linux `6.6.31+rpt-rpi-v8` に入っていたモジュール。試験後にSPIとMCPを標準版へ戻して復元を確認した。MCPパッチのソース比較に使った基準。[Raspberry Pi Linux c1432b4](https://github.com/raspberrypi/linux/tree/c1432b4bae5b6582f4d32ba381459f33c34d1424/drivers/net/can/spi/mcp251xfd)
- **結果表の対策前**は、すでに12ch化、SPI prefill、共有IRQの1巡化、IRQ分散を施した段階。対策後との差は、主にMCPのRX保護、FIFO計算、時刻管理の変更を含む候補版への切り替え。

## 構成と設定の変更

| 項目 | 4ch配布例・試験機の初期条件 | 12ch試験 |
|---|---|---|
| SPIの構成 | SPI0/1に各2台 | SPI0/1/3に各4台。各SPIにHATを1枚配置 |
| CAN配線 | 4ch配布例の構成 | 同じ番号のchを3枚で接続して4バス。各バス3ノードで、各送信元を2受信先が照合 |
| MCP発振子 | 20 MHz | 20 MHz、PLLなし |
| SPIクロック・CS保持 | 配布例では個別指定なし | 要求8.5 MHz、ログ上の実効約8.33 MHz、CS保持3 µs |
| SPI IRQ | affinityは0–3。初期観測では3本ともCPU0で処理 | SPI0→CPU1、SPI1→CPU2、SPI3→CPU3 |
| CANタイミング | FD 500 kbps／2 Mbps、SP 0.75／0.8 | 仲裁500 kbps、SP 0.875。FDのデータ区間2 Mbps、SP 0.8 |
| 送信キュー | 配布例は1000 | 試験時は100 |
| 割り込みまとめ処理 | 配布例では設定なし | RX/TXとも1フレーム、0 µs |
| FIFO配分要求 | 配布例では設定なし | Classic RX80/TX8、FD RX20/TX4。ドライバーへの配分要求値 |
| 受信バッファー | 実機初期の `rmem_max` は212,992 | 試験時8 MiB、アプリの `SO_RCVBUF` 要求4 MiB |

CS保持3 µsは今回の試験設定。より短い設定でSPIエラーが再現した初期比較を踏まえて選んだ。波形を計測した保証下限や、別配線での下限は未評価。

## ドライバー変更の経緯

1. **対象SPIを特定した。** 試験対象はRP1のDesignWare SPI。別のSPIを担当する `spi_bcm2835.polling_limit_us` の変更は対象経路に効かなかった。変更を戻した。
2. **共有IRQとCPU集中を対処した。** MCPの共有IRQハンドラーを1巡で返し、同じIRQを共有するほかのデバイスへ処理機会を返した。SPI IRQも3コアへ分散した。初期のFD 500 fps/ch比較では、1巡版で既定IRQ配分の20秒に受付エラー4,194件、IRQ分散後の60秒に0件を観測した。この比較は短時間の送信受付を評価している。
3. **SPI TX FIFOのprefill版を試験に採用した。** `spi_dw` に試験パラメーター `prefill_tx_fifo=1` を指定した。実機標準srcversionは `BDDA503547E217706FCF5B6`、試験版は `C9C60367C999F2297C242E6`。この資料で確認できるのは使用版と機能の概要までで、正確なソース差分と基準コミットの照合は未了。
4. **長時間のRX異常を連番で切り分けた。** 3時間の試験では通常のエラーカウンターが0でも、全方向の照合で欠落と重複が出た。別の自然観測では片側だけの重複、同じHW受信時刻、古いFIFO記録を確認した。Classicの観測例では重複6件と欠落6件が相殺され、受信総数は一致した。古いスロットを配信して消費を進める経路までを検証し、MCP内部とSPI経路のどちらで最初の不整合が発生したかは未確定。
5. **有効なRX記録だけを配信・消費する候補版を試した。** FIFOごとに最後の有効なHW受信時刻を持ち、古い記録を検出した位置で処理を止め、有効な先頭部分だけUINCする。空／満杯を含む受信可能数の計算とtimecounterの初期化・起動順序も変更した。共有IRQの1巡化は維持した。時刻を使う回避策はLinuxの既存修正を参考にした。[Linuxの回避策](https://github.com/torvalds/linux/commit/24436be590c6fbb05f6161b0dfba7d9da60214aa)・[MCP2518FD errata](https://ww1.microchip.com/downloads/aemDocuments/documents/APID/ProductDocuments/Errata/MCP2518FD-Silicon-Errata-and-Data-Sheet-Clarification-DS80000789.pdf)

MCPの標準srcversionは `25F70EFF03B462534F34E51`、1巡版は `726BD1D060EDC71AA977AFB`、最終候補は `F104131D3890560AA1274CD`。MCP保存パッチは5ファイルに158行追加・70行削除。これには1巡化と、SPI A/B試験用の上限パラメーター7行を含む。最終試験では上限8.5 MHzを指定した。行数にはSPI prefill側を含まない。

SPI 8.33 MHz／6.25 MHzの短時間比較は両方正常で、速度だけの効果は判定できなかった。人工FIFO注入と追加観測は切り分けに使い、最終3時間試験では外した。元版のFD 3時間と対策版の比較では、負荷を434 fps/chにそろえた。

## 確認した性能

| 条件 | 実送信時間 | 対策前の欠落／重複 | 対策後の欠落／重複 | 対策後の保護検出 |
|---|---:|---:|---:|---:|
| Classic 500 kbps、8 byte、960 fps/ch、計算負荷約70% | 約10,800秒 | 10／330 | 0／0 | 9回 |
| FD 500 kbps／2 Mbps、64 byte BRS、434 fps/ch、計算負荷約50% | 約10,800秒 | 2／130 | 0／0 | 7回 |

対策後Classicは全24方向で各10,368,000受信、FDは各4,687,200受信。両試験とも予定外受信、送信エラー、ソケットドロップ、不正データは0。保護検出数は古い記録で処理を止めた回数で、欠落・重複は連番の照合で別に判定した。負荷率はフレームのデータやスタッフビットを含めた計算値。[全24方向の受信照合 CSV](directions.csv)・[比較集計 CSV](runs.csv)

Classicの短時間探索では1100 fps/chを60秒・120秒で確認し、1125 fps/chの60秒では受付拒否が1,806件発生した。1600 fps/ch要求では1,152,000件中344,300件が拒否され、`tc` のキュー廃棄数と一致した。受付済み分の欠落・重複は0だった。1100 fps/chの長時間試験、対策後FDの高負荷長時間試験、40 MHzでの比較、レイテンシー分布は未評価。

## 検証の境界と公開範囲

試験プログラムは送信元IDと連番を照合し、送信受付が成功した集合を基準に、送信停止後に受信を待って各方向の欠落・予定外受信を判定した。重複は試験全体のカウンターで集計した。試験終了後は両モジュールを標準へ戻し、全12ch DOWN、IRQ affinity 0–3、`rmem_max=212992`、watchdog解除を実機で確認した。

このディレクトリが公開候補。実機ログ・原本アーカイブ・試験用バイナリー・機器固有設定は公開対象から外している。CSVは原本の測定値から必要な項目だけを抽出した。完全なビルド再現資料には、SPI prefillのソース差分と基準版の回収、カーネルパッチの出典・ライセンス表示、機器固有値を分離した12ch設定例が別途必要。

6.6.47の送信停止候補と今回の変更の関係は、別資料にまとめた。[カーネルソース比較](kernel-tx-comparison.md)
